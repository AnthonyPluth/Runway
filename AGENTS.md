# Agent guide

Instructions for AI coding agents working in Runway, a self-hosted personal finance app (Python backend in `runway/`, Svelte web app in `frontend/`, browser extension in `extension/`). Human contributors can use it too; [Development](docs/src/content/docs/contributing/development.md) has the long version, and the published docs are at https://anthonypluth.github.io/Runway/.

## Layout

- `runway/`: the backend, in packages whose imports `make lint` checks (import-linter's contracts in `pyproject.toml`):
  - `server/`: the HTTP handlers (`api/`), the background sync and the MCP server. Nothing else in `runway/` imports it.
  - `domain/`: what Runway works out from your data (`forecast.py`, `recurring.py`, `categorize.py`, `reports.py`, `networth.py`, `churning.py`, `retail/`, and so on).
  - `providers/`: the outside services (`plaid*.py`, `simplefin.py`, `carta.py`, `prices.py`, `finnhub.py`, `realie.py`, `webpush.py`). A provider doesn't import another; what they share has a module of its own (`banktx.py`, `banks.py`).
  - `storage/`: the database (`db.py`, `schema.py`, `models.py`, `settings_keys.py`, `secretbox.py`, `backup.py`) and `migrations/` (Alembic). It imports nothing above it, and only it imports the database drivers and Alembic.
  - At the top, what everything shares: `tls.py` (the only module that opens outbound connections), `validate.py`, `money.py`, `dates.py`, `monitoring.py`, `oidc.py`, `applock.py` (the app lock on top of sign-in).
  - `static/`: the served assets.

  A broken boundary fails `make lint`: move the code to where its import is allowed rather than adding an exception. A new provider module joins its provider's contract, or gets one of its own.
- `frontend/`: the web app (Svelte, Vite, Vitest, ESLint).
- `extension/`: the browser extension.
- `tests/`: backend tests, run with `unittest`.
- `tools/`: scripts for the repo itself; `feature_map.py` generates the feature map, `user_feature_map.py` the user-point-of-view one for the verify-runway skill (`make user-feature-map`; advice for it goes in `.claude/skills/verify-runway/references/feature-gotchas.md`), `api_contract.py` the API contract, `sync_screenshots.py` copies `make verify`'s screenshots into `screenshots/`.
- `docs/`: the documentation site (Starlight), published to GitHub Pages. Pages are Markdown in `docs/src/content/docs/`, one per part of the app under `using/`; their screenshots, and the README's, come from `screenshots/`, which holds a full-page screenshot of every page and flow at phone and desktop widths (taken at the iPhone 17 Pro Max's 440×956 and at 1280×800) and each page's first screen (`<page>-top-<width>.png`).

## Commands

Python goes through Poetry (Python 3.14).

- `make check`: each tool once: ruff, mypy, import-linter, Runway's own Semgrep rules, the Python tests (SQLite), the web app's type-check, ESLint, Vitest and build, and the docs site's build. Run it before pushing. The security scans (Semgrep's registry packs, Trivy, zizmor, pip-audit, npm audit, CodeQL) run only in CI.
- `make lint`: ruff, mypy, import-linter (the backend's import boundaries), ESLint and Runway's own Semgrep rules (`.semgrep/runway.yml`, run through `pipx`).
- `make test`: `poetry run python -m unittest discover tests`.
- `make test-parallel`: the same tests across 4 processes, as CI runs them (`make check` uses it); `make test-pg` runs them against `$DATABASE_URL` (Postgres), one process per CPU (4 to 16). `make test-timings` prints where the tests' time goes.
- `make frontend-check`: type-check, lint, Vitest and build for `frontend/`.
- `make fix`: apply ruff's safe fixes; review the diff afterward.
- `make verify`: runs the real app on demo data in a browser at phone (an iPhone 17 Pro Max, 440×956) and desktop widths, saving full-page screenshots (and each page's first screen) and a report to `artifacts/verify/` (demo data only). Verify what you changed: `PAGES="budget setup budget-edit"` runs only those pages (with the flows that start on them) and flows. Every page and flow runs on a demo server and a fresh copy of the demo data of its own, so flows must not depend on each other's data (a flow that needs some state gets it from the demo seed, `runway/domain/demo.py`, or its own steps) and a partial run writes exactly the images a full run does for those items. It runs `VERIFY_JOBS` of them at once (default the CPU count, at most 4, fewer when the machine is already busy; `1` is serial). One run at a time per machine (a second waits: "another verify is running on this machine, waiting..."); it waits for a busy machine to settle, retries a failed page or flow on fresh data, never keeps a half-loaded page, and writes its images only when everything passed. Its output also goes to `artifacts/verify-logs/` under a name of its own: don't redirect it to a fixed file name. Every page and flow is also audited for accessibility (`frontend/verify/a11y.mjs`: axe-core's WCAG 2.2 AA rules, a 44 px minimum tap target at phone width, a focus ring on every tab stop); a finding not in `frontend/verify/a11y-baseline.txt` fails, and so does a baseline line that no longer occurs (the list only shrinks: fix the finding, delete the line, never add one). A flow that opens something on an existing page (a dialog, a sheet) says `"inherits_page_baseline": true` with its `page` written out, and then also has the findings baselined for that page at the same width tolerated; a finding of its own (or of anything inside the dialog) still fails, so fix it. A failure ends with a `FAIL:` line per page or flow; [Development](docs/src/content/docs/contributing/development.md) says how to read one. The clock is frozen (the server and seed under libfaketime, the browser with Playwright's `page.clock`, at one day set in `runway/verify.py`), so two runs on the same tree write identical images; it needs Linux and `libfaketime` (`sudo apt-get install -y libfaketime`) and fails with that line without it.
- `tools/control`: drive the real app on demo data one command at a time (start a session, open a route, click, type, snapshot, screenshot, run a flow), to see your change working or reproduce a UI bug without writing a Playwright script. The [verify-runway skill](.claude/skills/verify-runway/SKILL.md) says when and how; `tools/control --help` lists the commands. After changing its help, run `make verify-skill` (`make fleet-checks` fails on a stale `references/cli.md`); `make control-smoke` runs it end to end.
- `make screenshots`: runs `make verify`, then makes `screenshots/` (committed) match it, only if every page and flow passed (otherwise it changes nothing). `PAGES="…"` updates just those images and leaves the rest. `make verify-twice` fails on any image that differs between two runs (the second one serial and in reverse order, so it also catches an image that depends on the worker count or the order). See "Git and PRs".
- `make fleet-checks`: the checks that replaced instructions, run by [fleet](https://github.com/AnthonyPluth/fleet) at the version `.fleet/version` names (`tools/fleet checks`, through `uvx`; part of `make check`), with Runway's values in `pyproject.toml`'s `[tool.fleet]` and its own checks in `tools/app_checks.py`: one Alembic head, a test in `tests/test_migrations.py` for each new migration, the workflows' conventions, the skills and the generated verify-runway references, the a11y baseline's form, and on your commits since `origin/main` the `Co-Authored-By` trailer, a `Removes-Test:` or `Skips-Test:` trailer on a commit that removes or skips a test, no new a11y baseline line, and no raster image added or changed outside the places images belong (see "Git and PRs"). Then `tools/fleet drift`: fleet's blocks in this file (between its `fleet:begin` and `fleet:end` marker comments) and the vendored `.claude/skills/fleet-*`, `.claude/agents/fleet-reviewer.md`, `.claude/hooks/fleet-session-start.sh` and `tools/fleet` are byte for byte fleet's at that version; they are edited in fleet, never here, and `make fleet-sync` brings them to the version the workflow pins carry (`.github/workflows/fleet-sync.yml` opens that pull request after a pin bump).
- `make feature-map`: regenerate the feature map; `make feature-map-check` checks it is current and every route has a test (part of `make check`).
- `make user-feature-map`: regenerate the verify-runway skill's user feature map (`.claude/skills/verify-runway/references/feature-map.md`); `make fleet-checks` fails when it is stale.
- `make api-contract`: regenerate the API contract (`docs/openapi.json`, `frontend/src/lib/api-types.ts`); `make api-contract-check` checks it is current (part of `make check`).
- `make pre-push`: about a minute: the feature-map, API-contract and fleet checks, and the tests that read shared fixtures (see "Before you push"). `make check` stays the one full run.
- `make docs`: the documentation site with live reload; `make docs-build` builds it and checks the links between pages.

## Starting work

<!-- fleet:begin starting-work v2.0.0 -->
- **One issue, one session, one pull request.** Work starts from an issue written as an agent task: its scope, acceptance criteria, dependencies and the model to use (see [CLAUDE.md](CLAUDE.md)). Start a fresh session for each one, on that model, rather than running many pieces of work through one long session.
- **Decisions belong in the issue.** If the issue doesn't settle something a user would notice, ask instead of choosing. Otherwise keep existing behaviour exactly; a change that isn't asked for is a regression.
- **Done means checked.** An issue says how its result is checked (`make check`, a test that fails before the change, `make verify` for anything on screen where the repository has it); the pull request shows that output, not a description of it.
- **Verify in proportion.** Run the tests your change touches while working, and `make check` once before pushing.
- **A correction becomes a check.** When a mistake is pointed out, fix it and add what would have caught it: a lint rule, a type, a test, or a check `fleet checks` runs ("Mistakes that keep coming back" says how). A sentence in this file is the last resort, for what no check can express.
- **Parallel work stays apart.** Agents working at once take separate areas. Two pull requests that change the same files, or both add a migration, land one at a time: the second merges `main` in and re-runs its checks.
<!-- fleet:end starting-work -->
- **Postgres is CI's job.** CI runs the Postgres suites on every pull request: run `make test-pg` yourself only for changes to the database, migrations or tests (see "Tests that share the database" below), on a database of your own that you drop afterwards.

## Working in a container

<!-- fleet:begin working-in-a-container v2.0.0 -->
- **Start the session in the repository.** The session-start hook (in `.claude/hooks/`) sets up the toolchain, Poetry's environment and the web app's packages, but only for a session whose project directory is this repository. A session started one level up has none of it: the system `python3` lacks the dependencies, and the tests fail on their imports.
- **Run Python through `poetry run` or `make`** (`make test`, or `poetry run python -m unittest tests.test_x`), never the bare `python3`. `make setup` installs the dependencies by hand.
- **Subagents make their own worktree** under `.claude/worktrees/` (ignored by `.gitignore`), from the session's checkout, and push from there. A session whose working directory isn't a git repository can't create one for them.
- **Skills have two homes.** fleet's skills are under `.claude/skills/fleet-*` and are changed in fleet; the app's own are under `.claude/skills/`; skills go nowhere else (`fleet checks` checks it: `skill-homes`).
<!-- fleet:end working-in-a-container -->
- **Some checks only run in CI.** Locally: ruff, mypy, import-linter, Runway's Semgrep rules, the Python tests on SQLite, the web app's checks, the docs build, the fleet, feature-map and API-contract checks. Only in CI: the Postgres suites (`make test-pg` needs a database of your own), the Docker image build and run, the Verify flows check (`.github/workflows/verify.yml`, only on changes under `frontend/`, `runway/domain/demo.py`, `runway/verify.py`), the security scans, Codex's review and, on a risky pull request, the Claude "Second review". A push reaches them; a local run doesn't.
- **A forecast or money-math test starts from `tests/forecast_support.py`'s `card_setup`** and the helpers in `tests/shared.py`: `self.acct`, `self.stmt` (the issuer's statement), `self.manual` and `self.tx(..., pending=1)`. Build the case in a few lines with made-up figures, as `tests/test_forecast_*.py` do, and prove the test fails before the fix.

## Start from the feature map

[`docs/feature-map.json`](docs/feature-map.json) (readable as the [Feature map](docs/src/content/docs/contributing/feature-map.md) page) lists every API route with its handler, the web app files that call it, the tests that exercise it and the docs page that describes it. Start there to find where a feature lives. It is generated: after changing routes, `api(` calls, tests or docs, run `make feature-map` and commit the result (`make check` and CI fail when it is stale). A new route needs a test; `tools/feature_map_allowlist.txt` holds the routes that had none, and only shrinks.

## Conventions

- Match the surrounding code's style, comment density and naming. Ruff and mypy config live in `pyproject.toml`; don't silence a rule to get green.
- One paved path; lint fails on the old way (`.semgrep/runway.yml`, `frontend/eslint.config.js`). Fix a finding with the helper, or justify it with an inline ignore and a reason; don't switch the rule off. Python: HTTP only through `tls.urlopen` (no `urllib.request.urlopen` or `build_opener` outside `runway/tls.py`); request bodies in `runway/server/api/` through `runway/validate.py` (no `bool(body…)`, `float(body…)`, `int(body[…])`); no SQL built from strings (`sa.text(f"…")`); the half cent is `money.CENT` (no `0.005` outside `runway/money.py`); sync and provider modules take the `today` they're given (no bare `date.today()`); no `datetime.utcnow()`; month arithmetic only in `runway/dates.py`. Web app: `errMsg(e)` from `lib/act.ts`, not `(e as Error).message`; `fetch(` only in `lib/api.ts`; `.catch(() => {})` carries a comment saying why; account kinds come from `lib/accounts.ts`, not a hand-written list.
- Real typography (’ – −) in user-facing strings and comments is intentional; don't "fix" it to ASCII.
- Schema changes need an Alembic migration in `runway/storage/migrations/`, numbered after main's newest, with its own `test_<revision>_…` in `tests/test_migrations.py` (checked). A new database is made from `schema.py` in one step (`db.create_fresh`), not by replaying the migrations, so `schema.py` must give exactly the tables the migrations leave, column order included: a column a migration adds goes last in its table (checked: `tests/test_fresh_database.py`).
- The API contract: a route it covers has its reply and body types in `runway/server/contract.py`, on its handler's annotations, and the web app calls it with `apiCall<"METHOD /path">(…)` from `lib/contract.ts`. Change a covered reply or body there, run `make api-contract` and commit the generated files; cover a route the same way (see [Development](docs/src/content/docs/contributing/development.md), "API handlers").
- A change users or contributors would notice updates its page in `docs/src/content/docs/` in the same PR. Link between pages with absolute paths (`/Runway/start/docker/`); a broken one fails the build.
- Add or update tests with the change. Don't skip, disable or delete a test to get CI passing; when one really goes, a `Removes-Test:` or `Skips-Test:` trailer says why (checked).
- Never commit secrets. `.env.example` lists configuration; real values stay in `.env`.
- Read `SECURITY.md` before touching auth, encryption or anything that handles bank credentials.

## Mistakes that keep coming back

<!-- fleet:begin mistakes v2.0.0 -->
**A mistake that repeats gets a check.** When review flags the same kind of mistake on a second pull request, the fix adds a check that would have caught it: a lint rule (ESLint, or Semgrep in `.semgrep/` with a failing and a passing example), a type (strict mypy, a `NewType` or `Literal`), or a test. The item below then names that check in its parenthesis (`checked: waypoint-trip-visibility`, `checked: tests/test_offline.py`). An item stays *human-judged* only when no check can express it, and says why. Every month the "Repeated review findings" issue lists the kinds that came back; a row there is closed by a check, not by a new sentence here.

Review findings on agents' pull requests fall into the same few kinds: check your change for each before you push. The reviews read agents' pull requests for the *human-judged* ones: the "Second review" on a risky pull request, the independent "Agent review" on every agent's pull request where the app turns it on, and the code-review bot the repository uses. A blocking finding fails the merge gate, and so does an open P1 or P2 review thread from that bot (the gate counts only the authors in its `blocking-thread-authors`).

- **Failure paths** (human-judged: what a person should see when something fails is a product decision, which no rule can see). For every new error, rejection or early return, know what the user sees, and test it. Don't leave stale state that says things are fine: a scan or sync that half-fails must not clear the last warning, a failed reload must not leave old data on screen looking current, and a job that couldn't start isn't a failed run.
- **Access that outlives the person** (human-judged: each new kind of credential is new code that no existing check knows; its own test holds it once written). A new kind of session, grant, token, key or connection must end when its owner can no longer sign in, like browser sessions do; test that it does.
- **Undo and restore** (human-judged: which values are awkward depends on the data; the round-trip test holds each case once written). Putting something back restores exactly what was there, without normalizing it on the way; test the round trip with awkward values.
- **GitHub Actions** (partly checked: `fleet checks` checks bash by default, SHA pins with a version comment, paginated `gh api` lists, step-only contexts in a workflow's or job's `env:` and every `runs-on:`; zizmor checks `persist-credentials`, template injection and pinning; concurrency groups and agents' allowed commands are human-judged, because the right group and the commands an agent needs depend on what the workflow does). Workflows run bash with `-eo pipefail` (each file's `defaults`); keep it. On a pull request's `closed` event `github.ref` is main's, so build concurrency groups from `github.event.pull_request.number`. Check out with `persist-credentials: false`, pin actions by SHA with the version in a comment, pass event values to scripts as environment variables, paginate `gh api` lists, and allow an agent only the exact commands it needs. Run zizmor on a workflow you change.
- **Layout** (human-judged: whether a page reads well at a width is a judgement, which no rule can make; the screenshots at both widths show it). A layout change is checked at phone and desktop widths, not only the one it was written at.
- **Verification that doesn't cover the change** (partly checked: `fleet checks verification`; coverage is judged by the review). Where the app sets `[tool.fleet.verification]`, the pull request's Verification table names every behaviour the change touches as a dimension: `verified` with evidence that exists in the diff or the tree and exercises the change, or `not verified` with why and what would close the gap. A `verified` claim whose evidence doesn't exist, or a changed behaviour missing from the table, is blocking; a vague gap reason is advisory.
<!-- fleet:end mistakes -->

Runway's own, after fleet's shared ones (a check for one of these goes in `.semgrep/runway.yml`, `frontend/eslint.config.js` or `tools/app_checks.py`):

- **Tests that share the database** (human-judged). On Postgres every test module shares one schema, and CI runs modules in parallel. A test that writes settings, or runs a sync, the AI categorizer or a request through the server, takes its own database with `tests/shared.py`'s `own_database(self)`: on Postgres a schema borrowed from the test process's pool (made once, emptied when the test ends, never held by two tests at once), on SQLite a file of its own. Run the Postgres tests before pushing a change to tests (docs/src/content/docs/contributing/development.md, which also has the throwaway Postgres's flags: for tests only, never for the image, the Compose files or a real database). In Vitest, use fake timers for anything debounced, so a save doesn't leak into the next test.
- **Private data in logs** (human-judged). Logs and error pages never carry amounts, merchants, account ids, query strings or credentials; that includes exception text (a database error names the row it was writing). Go through `monitoring.scrub` (or `monitoring.report` for an error), and test what's logged.
- **Personal financial data in the repo** (human-judged). The repository is public. Never put data read from anyone's instance (balances, amounts, merchants or payees, card or account names, lenders, budgets, income, dates of real transactions, people's names) into PR titles or descriptions, review replies, issues, commit messages, code comments, tests, fixtures or docs, even to explain a bug. Describe the case in general terms and use made-up figures and names (as `tests/` does).
- **Time zones** (partly checked: lint rejects a bare `date.today()` in sync and provider modules and `datetime.utcnow()`; the rest is human-judged). "Today" and the daily sync's hour are the machine's local time (`TZ`). Anything that tells another system about a time (a schedule, a timestamp) carries the same zone, not UTC by default.
- **Tablet layout** (human-judged: `make verify` has no tablet width). `make verify` checks a layout change at phone and desktop widths (fleet's "Layout" above); a change that touches the 768–1023 px rail layout is also looked at by resizing a browser there, and nothing of that is committed.

## Before you push

Each push starts CI and the reviews `.github/workflows/agent-review.yml` runs, so find what you can locally and push once. The cloud container is a shared machine that can't run the whole suite, so run the targeted checks:

- The tests for what you changed, then `make pre-push`. It covers what most often fails CI because a change leaks into a shared fixture: new demo data in `runway/domain/demo.py` (`demo.seed` is read by `test_demo`, `test_api_contract`, `test_api_handlers`, `test_api_queries`, `test_api_validation`, `test_budget_*`, `test_churning_api` and `test_backup`; put data only one test needs in that test); a new route missing from `tests/test_api_contract.py`; a forecast change that moves `tests/fixtures/forecast_golden.json` (regenerate it only when the change is meant to); generated files that weren't regenerated (`make feature-map`, `make api-contract`); and a schema change's migration, its `test_<revision>_…` and the backup tests.
- Put a test method directly under its own decorators: one added between a `@unittest.skipIf` and its test takes the skip.
- For web app changes run `make lint` and `make frontend-check`. If ESLint or svelte-check won't start in a fresh container (`Could not find "svelte" in plugin "svelte"`, missing `esrap` types), `frontend/node_modules` is incomplete: `cd frontend && rm -rf node_modules && npm ci` (the session-start hook does this when it finds it: `.claude/hooks/fleet-session-start.sh`, with what to check in `.claude/hooks/fleet.conf`'s `NODE_CHECK`). Don't push to let CI report the error.
- When something fails that you didn't expect, find the cause (run the one test, read the traceback) before changing anything, and put all the fixes in one push. A guess that needs CI to confirm costs a whole cycle.

## Git and PRs

- **Screenshots live in one committed directory, `screenshots/`**, not one per PR: a full-page screenshot of every page and flow at phone and desktop widths (`<name>-<width>.png`) and each page's first screen (`<page>-top-<width>.png`, which the README and the docs show); there is no tablet image. A PR that changes the UI runs `make screenshots` before its last push (`PAGES="…"` for the pages it touched while working; the full run is what catches a leak) and commits what changed, never images copied in by hand, so the UI change shows as image diffs in the PR's Files changed (GitHub's 2-up, swipe and onion-skin views). The only images a change commits are the ones `make verify` writes (`make screenshots` copies them into this directory): they are the visual regression baselines, so show a before and after through those images' diff in the PR, never a hand-made comparison file (`make fleet-checks` fails one: a raster image that is not a page or flow image `make verify` writes into `screenshots/`, or an icon or logo in `extension/icons/`, `runway/static/` or `docs/src/assets/logo.png`). Commit all of the directory's changes, including pages you didn't mean to touch: an unexpected diff is the check that the change didn't leak. The demo data's clock is frozen, so an image changes only when the UI or its data does; a diff on a page you didn't touch is a leak (or a nondeterminism bug: report it). The PR gets a comment from the Screenshot diff workflow automatically, with a link to `report.html` (an unzipped artifact: for each changed screenshot the tabs Reference, Actual and Slider, with boxes around what changed that a checkbox hides; you must be logged in to GitHub to open it) and a line of counts, so don't compare screenshots by hand. Only `make verify`'s made-up demo data is ever committed: the repository is public. `make verify` captures the dark theme only, so check the light theme yourself for a theme-sensitive change, and say so. Skip it for a PR with no UI change, and say so in the description.
- `make pre-push` before each earlier push, `make check` before the last (below). A review thread with a P1 or P2 badge from Codex also fails the merge gate until the thread is resolved: resolve it once the finding is fixed or answered, then run the Merge gate workflow by hand or push (resolving starts no workflow). The gate also stays pending until Codex has reviewed the head commit (`require-codex-review` in `merge-gate.yml`), so a draft needs an `@codex review` comment after each push (Codex doesn't review a draft by itself).

<!-- fleet:begin git-and-prs v2.0.0 -->
- Work on the branch you were given; never push to `main`.
- Keep commits focused, with a clear message. An agent's commit ends with a `Co-Authored-By: Claude <Model> <version> <noreply@anthropic.com>` trailer naming the model that wrote it (checked on every pull request).
- Before pushing to a pull request, run `make check`.
- Open a pull request for every change, once it's pushed, as a draft, and summarize what changed and why. Keep the description short and professional: a few bullets on the change and how it was tested, not an essay. Don't say who asked for it or reported it.
- Keep a pull request a draft until every check is green, every review has finished and every comment is addressed. Right after opening the draft, comment `@codex review` on it if the repository uses that reviewer (it doesn't review a draft by itself, but that comment asks it to), and again after a substantive push. Mark it ready for review only when every check is green, every review that runs on it has finished (the "Second review", the independent "Agent review" where the app turns it on, and any such reviewer), and every review comment has been fixed or answered and resolved. Then watch it until it merges.
- A pull request's title decides the next version when it's merged: `feat: …` releases a minor version, `fix: …` or anything else a patch, and `feat!: …` (or a `BREAKING CHANGE:` line) a major one, for a change that breaks an existing setup.
- Where the app sets `[tool.fleet.verification]`, a pull request's description carries a Verification block (the table between the `fleet-verification` markers: each dimension of the change `verified` with its evidence, or `not verified` with why) before it is marked ready, written with the `fleet-verify-change` skill; `fleet checks` reads it.
- A pull request is ready when its "Merge gate" check passes: every check green, including the "Second review" with no blocking finding (it reviews a risky pull request, labelled `safety-critical` or `security` or touching the paths the review lists, and passes any other as not risky), no open P1 or P2 review thread from the code-review bot the gate counts (its `blocking-thread-authors`), and, where the app turns it on, the independent "Agent review" with no blocking finding. Dependabot's updates merge themselves through it.
- Don't hard-wrap lines in pull request descriptions, comments, issues or the body of a commit message: write each paragraph or list item as one line, and let GitHub wrap it to the screen. Only code and repo files keep their own wrapping. Keep the commit subject to one short line.
<!-- fleet:end git-and-prs -->

## Model routing

See [CLAUDE.md](CLAUDE.md) for which model to use for which kind of task.
